# 週刊オカルト新聞（構想・仕様メモ）

## コンセプト

HATAKITI.comの新規独立コンテンツとして「週刊オカルト新聞」を追加する。

単なるRSSアグリゲーションや転載ではなく、複数の公開情報源から1週間分のオカルト関連情報を収集し、AIが同一案件・類似案件・関連テーマを整理したうえで、週刊号として編集・公開する。

正式名称：**週刊オカルト新聞**

※「HATAKITI OCCULT WEEKLY」を新聞の正式な題字・マストヘッドとして使用しない。

## 基本フロー

1. 毎日1回、新着情報を取得
2. 重複を除外して1週間分を蓄積
3. 週1回、AIが全データを解析
4. 同一案件・類似案件・関連テーマをクラスタリング
5. 情報量・複数ソースでの扱い・関連度などを基準に重要度を判定
6. 大記事・中記事・小記事へ編集
7. 「週刊オカルト新聞」として1週間につき1号を生成
8. PDFを主成果物として公開し、過去号をアーカイブする

## 情報源

初期候補は以下。

- Webムー
- TOCANA

実装前に、公式RSS・公式フィード・公式API等の利用可能な取得方法、利用規約、robots.txt等を確認する。

利用条件上問題のない方式のみ採用する。

元記事本文の全文コピー・転載を目的としない。HATAKITI.com側では、複数情報を整理・比較・要約した独自の週刊編集記事を生成する。

## 週次編集ルール

### 大記事

- 複数の記事・複数情報源で扱われた同一案件
- 1週間の中で情報量・関連度が最も高い案件

同一案件に関する複数情報を統合し、今週のトップ記事として大きく扱う。

**本文は原則800〜1200字程度。**

読者が元記事を開かなくても、何が起きたのかを理解できることを必須とする。出来事の概要だけでなく、確認できる範囲で背景、経緯、現在分かっていること、不可解な点・争点などを整理して記事化する。

### 中記事

複数の関連情報が存在するテーマをまとめる。

例：

- 今週のUFO・UAP
- 今週の心霊・怪談
- 今週のUMA
- 今週の古代文明

**本文は原則500〜800字程度。**

単なる短い紹介ではなく、出来事の概要、経緯、注目されている理由が分かる記事にする。

### 小記事

他の記事との関連が少ない単独案件。

**本文は原則200〜350字程度。**

短い記事であっても、読者が「何が起きたのか」を本文だけで理解できる完結した記事とする。公開ページでは本文を途中で省略しない。

## 記事の基本原則

週刊オカルト新聞の記事は「ニュースの要約」ではなく、**新聞記事として読める独自編集記事**であることを基本とする。

出典リンクは、リンク先を読まなければ内容が分からない状態を補うためのものではない。まずHATAKITI側の記事だけでニュースの概要・経緯・現在分かっていることが理解でき、そのうえで「もっと詳しく知りたい」読者が元記事を追えるようにする。

記事では可能な範囲で次の順序を意識する。

1. 何が起きたのか
2. いつ・どこで・誰が関係したのか
3. これまでの経緯
4. 確認されている情報と未確認情報
5. オカルト的に興味深いポイント
6. 現時点での結論・未解明点

入力情報に存在しない事実を創作して文字数を増やしてはいけない。情報が不足している場合は、不足していることを明示する。

## AIの役割

AIは以下を担当する。

- テーマ分類
- 同一案件の判定
- 類似案件のクラスタリング
- 関連テーマの整理
- 重要度判定
- 大記事・中記事・小記事の編集
- 記事本文の執筆
- タグ生成

AIは推測で事実を補完しない。

特にUFO、心霊、予言、陰謀論、超常現象等については、「報じられている内容」「確認されている情報」「未確認情報」を可能な限り区別する。

## 情報源の明示（必須）

週刊オカルト新聞では、**すべての大記事・中記事・小記事ごとに、その記事生成に使用したニュースソースを必ず明示する。**

新聞全体の末尾に媒体名だけを列挙する方式では不十分とする。

各案件について保存・表示する情報：

- 媒体名
- 元記事タイトル
- 元記事URL
- 元記事公開日（取得可能な場合）

AIが複数の記事を統合して1つの案件にした場合も、使用した元記事をすべて表示する。

リンク先は媒体トップページではなく、**実際に参照した元ニュース記事のURL**とする。

読者がHATAKITI.comの記事から、気になった情報の元記事を追跡できることを必須とする。

## 新聞レイアウト

HATAKITI.comの黒基調デザインと統一する。ただし、PDFを主成果物とし、新聞としての紙面設計を最優先する。

### 基本紙面仕様

- A4縦
- 1ページを3段の水平帯として扱う
- 本文フォントサイズは全記事で統一する
- 本文の文字幅・行送りは固定値として扱う
- 記事は原則として1ページ内で完結させ、ページまたぎを基本パターンにしない
- 見出しは本文より大きくするが、見出しサイズは記事重要度に応じて定義する
- 記事境界は罫線・余白・見出しによって明確にする

### 組版の基本思想

組版は「PDFを描画しながら空いた場所を埋める」方式ではなく、**記事の文字量を先に分析してから紙面を設計する方式**とする。

基本処理順序は以下とする。

1. A4紙面の物理寸法を確定
2. 上下左右余白等を差し引き、利用可能紙面を算出
3. 利用可能紙面を3段に分割
4. 本文フォント・文字幅・行送りから本文文字マス容量を算出
5. 各記事について本文文字数、見出し、媒体名・日付等のメタ情報、記事間余白を含む必要容量を算出
6. 1ページに入れる記事の組み合わせを探索
7. 小記事を積極的に組み込み、自然な範囲で空白率を下げる
8. 記事量に適した新聞組版トポロジーを選択
9. 記事文字数・必要容量に応じて縦罫線位置や各領域の幅を動的に調整
10. 全記事が完全に収まることを確認してからPDFを描画

**組版パターンは固定寸法のテンプレートではない。** パターンは「記事領域同士がどのようにつながるか」というトポロジーを定義するものであり、実際の縦罫線位置・領域幅・記事領域の大きさは記事の文字数と見出し等の必要容量に応じて調整する。

### 文字容量の考え方

紙面容量は、単純な「1ページ＝固定○文字」ではなく、**本文文字マス**を基本単位として計算する。

本文について、概念上以下を固定する。

- `PAGE_WIDTH` / `PAGE_HEIGHT`
- `MARGIN_TOP` / `MARGIN_BOTTOM` / `MARGIN_LEFT` / `MARGIN_RIGHT`
- `HEADER_HEIGHT` / `FOOTER_HEIGHT`
- `BAND_COUNT = 3`
- `BODY_FONT_SIZE`
- `BODY_CHAR_WIDTH`
- `BODY_LINE_HEIGHT`

利用可能高さを `H` とすると、基本段高は `H / 3` とする。

ある記事領域の本文容量は、領域の高さと幅から求める。

- 1列あたりの本文文字数 = `floor(本文領域高さ / BODY_LINE_HEIGHT)`
- 本文列数 = `floor(本文領域幅 / BODY_CHAR_WIDTH)`
- 本文容量 = `本文列数 × 1列あたりの本文文字数`

見出し、媒体名、公開日、その他のメタ情報、記事間余白は、それぞれが実際に占有する物理領域または本文文字マス相当量として計上する。

記事の必要容量は概念上、

`ARTICLE_REQUIRED_CAPACITY = BODY_CHAR_COUNT + HEADLINE_EQ + META_EQ + SPACING_EQ`

とする。

ただし、`HEADLINE_EQ`、`META_EQ`、`SPACING_EQ` は固定文字数を適当に加算するのではなく、実際のフォントサイズ・文字幅・行送り・配置領域から算出する。最終的な収容判定は、記事領域の実容量が記事の必要容量以上であることを条件とする。

本文フォントサイズを記事ごとに変更して容量を合わせることは禁止する。

### 記事の組み合わせと入れ替え

1ページに入れる記事は、重要度順に単純に詰め込むのではなく、記事の必要容量と組版トポロジーを組み合わせて探索する。

例えば大記事・中記事だけでは余白が大きくなる場合、200〜350字程度の小記事を適切な空間へ組み込むことで紙面利用率を高める。

したがって、記事選択では、

- 大記事・中記事・小記事の組み合わせ
- 各記事の文字量
- 各記事の見出し等による追加容量
- 組版トポロジーへの適合性
- 空白率

を総合的に評価する。

小記事は「余った場所に置く最後の部品」ではなく、**紙面全体の空白率を自然に下げるために積極的に利用する記事**として扱う。

ただし、空白率を下げるために記事を不自然な形へ押し込んだり、記事本文を途中で切ったりしてはならない。

### 組版トポロジー

組版パターンは、あらかじめ新聞として自然なものを複数定義し、その中から記事量に適したものを選ぶ。ただし、寸法は固定しない。

#### 2記事の基本パターン

基本形は以下のような、3段を通して境界が一方向へ移動する形とする。

```text
┌──────────────────────┐
│          A           │
│                      │
├───────────┬ - - - - -┤
│     B     │    A     │
│           │          │
├ - - - - -┴───────────┤
│          B           │
│                      │
└──────────────────────┘
```

すなわち、上段全面をA、中段をB/A、下段全面をBとする形を基本とする。

ただし、記事境界が明確で新聞として自然に成立する場合は、例えば以下のような応用形も許容する。

```text
┌──────────────────────┐
│          A           │
│                      │
├───────────┬───────────┤
│     B     │     A     │
│           │           │
├───────────┼───────────┤
│     B     │     A     │
│           │           │
└──────────────────────┘
```

一方、上下反転型や、A/B/A/Bのように境界が不自然に蛇行する形は基本パターンとして採用しない。

#### 3記事の応用パターン

例えば以下のような連鎖型を許容する。

```text
┌──────────────────────┐
│          A           │
├───────────┬ - - - - -┤
│     B     │    A     │
├ - - - - - ┴───────────┤
│     B     │    C      │
└──────────────────────┘
```

これは「3記事だから3等分する」という意味ではない。A・B・Cそれぞれの文字量に応じて縦罫線位置を調整し、最も自然に収まる位置を決定する。

4〜5記事についても、単純な十字型や機械的な均等分割を優先せず、記事量と紙面利用率に応じた互い違い・連鎖型の新聞組版を基本とする。

### 罫線ルール

記事境界は読者が記事の範囲を迷わないことを最優先する。

- 通常の記事境界は実線を基本とする
- 段の切り替わりで記事境界の接続を示す部分は、必要に応じて破線を使用する
- 破線は「同じ記事の続き」を示す記号ではなく、記事境界の幾何学的な接続を新聞的に見せるための表現として扱う
- 記事境界を曖昧にする装飾は禁止する
- 紙面全体を機械的なマス目で囲うのではなく、必要な記事境界だけを描画する

### 組版候補の評価

成立しない候補は評価対象から除外する。最低限、以下の順序で評価する。

1. 全記事が完全に収まる
2. 記事がページ内で完結する
3. 見出し・媒体情報・記事境界が明確である
4. 新聞として組版が自然である
5. 小記事を有効に活用できている
6. 紙面の空白率が低い

「空白率が低い」ことだけを理由に、不自然な組版を採用してはならない。

### 組版とPDF描画の責務分離

組版エンジンとPDF描画エンジンの責務を分離する。

組版エンジンは、

- どの記事をどのページに配置するか
- どのトポロジーを使うか
- 各記事領域をどの大きさにするか
- 縦罫線をどこに置くか
- 各記事が完全に収まるか

を決定する。

PDF描画エンジンは、組版エンジンが決定した領域へ、見出し・本文・媒体情報・罫線等を正確に描画する。

**PDFを描画してから空白を見つけて記事を押し込む方式に戻してはならない。**

## トップページからの導線

トップページから週刊オカルト新聞へ直接移動できる入口を必ず設ける。

トップページには、可能であれば最新号の紹介カードも表示し、

**トップページ → 週刊オカルト新聞 → 最新号 → 各記事 → 出典**

という自然な導線を作る。

「週刊オカルト新聞」が存在することを訪問者が自力で探さなくても分かることを重視する。

Web版の記事全文をPDFと別に作ることは基本要件とせず、Web側は最新号・過去号・PDFへの導線を中心とする。

## WordPress構造

通常のブログ投稿とは分離し、専用Custom Post Type等の専用データ構造を使用する。

想定識別子：`occult_weekly`

1週間につき1号を保存し、最新号と過去号アーカイブを提供する。

## 自動実行

2段階処理とする。

### 毎日

新着情報の取得・重複除外・蓄積。

### 毎週

1週間分をAIが編集し、週刊号を生成・公開。

WordPressアクセス依存のWP-Cronだけでなく、ConoHa側のcron等、安定した実行方式を実装時に検討する。
